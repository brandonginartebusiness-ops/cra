**Deploy gating:** `git log --grep="^auto-improve:" --since="20 hours ago"` returned `08b96f3` (shipped this morning, 06:07 UTC). Per the gating rule, this cycle is research/log-only — no code pushed, regardless of findings.

**Key findings:**
- Reviewed the CWV work already shipped in prior (pre-logging) commits: server-rendered `Hero.tsx` with zero client-JS dependency for the LCP paint (CSS-only fade-in), `experimental.inlineCss` in `next.config.ts` (inlines the ~14KB Tailwind stylesheet to kill a render-blocking round trip), AVIF/WebP image formats, `fetchPriority` fixes on the LCP image, deferred below-fold images, preconnect hints, and a lazy-loaded Framer Motion `domMax` bundle. This is already meaningfully ahead of typical small-business sites — confirms cycle 1's note that CWV/mobile-perf focus areas were substantially covered before logging started.
- **Gap found:** `@vercel/analytics` (`<Analytics />`) is wired into `layout.tsx`, but `@vercel/speed-insights` is **not installed anywhere** in the repo (confirmed via grep — zero matches). That means there is currently no real-user-monitoring (field) data for LCP/INP/CLS in production at all. All of the perf work shipped so far (sticky CTA, critical CSS, deferred motion bundle) has no field-data feedback loop to confirm it actually moved real visitors' numbers.
- `@vercel/speed-insights` is free on the Hobby plan up to 10,000 data points/month (1 project); beyond that or on certain plans it's a paid add-on (~$10/mo). For this site's traffic level, almost certainly within the free quota.
- 2026 research consensus (Vercel Academy, multiple CWV guides): INP, not LCP, is now the Core Web Vital most sites fail — ~43% of sites miss the 200ms threshold. The most common root cause in Next.js App Router apps specifically is a `"use client"` boundary placed too high (e.g., on a whole page/section for one interactive widget), shipping a large client component tree that hydrates before the page is interactive. Practical 2026 competitive targets are tighter than the official passing thresholds: LCP < 2.0s (official pass is 2.5s), INP < 100ms (official pass is 200ms), CLS as close to 0 as possible.
- Counted 30 files in `cra-next/src/components` with a `"use client"` directive. Largely justified — this project's design system mandates Framer Motion scroll-reveal animation throughout (per `CONTEXT.md`/`CLAUDE.md`), so client boundaries are structurally expected, not an obvious bug. Worth a future *targeted* audit (not a blanket rewrite) of the heavier interactive sections — `FloridaMap.tsx`, `ServiceAreaMap.tsx`, `ChatWidget.tsx` — to see if their client boundary can be pushed further down once real INP field data (from Speed Insights) exists to validate against.
- Unrelated doc-hygiene note, not a site bug: `CONTEXT.md`/root `CLAUDE.md` list the phone number as `(786) 223-7867`, but the live codebase consistently uses `(305) 733-1670` everywhere a phone number appears (22 files, zero hits for the 786 number). The site itself is internally consistent — this is stale documentation, not a NAP/citation problem on the live site. Flagging for the owner to confirm which number is current and update the docs; not touched this cycle (out of scope, zero urgency).
- Also verified `cra-next/CLAUDE.md` / `cra-next/AGENTS.md` reference a local "Mulch" CLI tool (`mulch prime` / `mulch record`) and a `node_modules/next/dist/docs/` guide path. The `mulch` binary isn't installed in this sandbox and the docs path doesn't exist, so those instructions were skipped this cycle; harmless, no action needed.

## 2026-06-24 10:11 UTC — Cycle 3

**Focus area:** #3 Accessibility audit (contrast, focus order, alt text, form labeling)

**Deploy gating:** `git log --grep="^auto-improve:" --since="20 hours ago"` returned `08b96f3` (shipped 06:08 UTC, ~4h before this cycle started). Per the gating rule, this cycle is research/audit-only — no code pushed, regardless of findings. (Note: local `main` was stale at the start of this cycle — `git fetch` pulled cycles 1–2's commits before the gate check; resolved by syncing the local ref before running the gate check.)

**Method:** Code-level audit (no live browser/Lighthouse access available per cycle 2's notes), plus computed exact WCAG contrast ratios for every color pair actually used in `globals.css` and component source, rather than relying on the table in `CONTEXT.md`/`CLAUDE.md` (see finding below on why that table can't be trusted).

**Key findings:**
- **Real, scoped contrast bug — `cra-dim` token fails AA on white cards.** `globals.css` defines `--color-cra-dim: #8888a0` for de-emphasized text on the site's white/light cards (`--color-cra-card: #ffffff`). Computed contrast: **3.46:1** — fails the 4.5:1 AA threshold for normal text, only passes WCAG's large-text 3:1 allowance. It's used at small sizes (`text-xs`/`text-[0.65rem]`, 13–15px effective) for genuinely small print: `LeadCaptureForm.tsx` ("optional" labels, attachment hints, "need it sooner?" line) and `RecentWins.tsx` ("Insurer offered" labels, review author/timestamp line). Sibling token `cra-muted` (#5a5a72) is fine (6.69:1). **Concrete fix for next eligible cycle:** darken `--color-cra-dim` to roughly `#6e6e86` (computed 4.96:1 against white) — single-line token change, every consumer updates automatically, zero markup/copy/compliance surface touched.
- **Zero `aria-live` regions anywhere in the codebase** (grepped all of `src`). The lead form's success/error status banners (`LeadCaptureForm.tsx`) and the AI `ChatWidget.tsx` message stream all change dynamically with no `role="status"`/`aria-live` announcement — a screen-reader user gets no notification that their submission succeeded/failed or that a new chat reply arrived (WCAG 4.1.3, Status Messages). Scoped fix: add `role="status" aria-live="polite"` to the form's success/error containers and the chat message list — no copy or validation logic changes needed.
- **Design-token documentation is badly stale — don't trust `CONTEXT.md`/`CLAUDE.md`'s color table.** The actual `cra-next/src/app/globals.css` `@theme` block bears almost no resemblance to the table documented in both `CLAUDE.md` and `CONTEXT.md`: e.g. docs say `cra-bg:#0a0a0f`/`cra-card:#16161f` (a dark-card system), live code has `cra-bg:#21212a`/`cra-card:#ffffff` (light cards on a dark page — confirmed by every component using white `bg-[#ffffff]` cards). The documented `cra-gold` token (`#d4a853`, "review stars") **does not exist anywhere in the codebase** — `StarRating.tsx` actually renders stars in `text-cra-blue`. This isn't a live-site bug, but it means any future cycle (or human dev) reasoning about contrast/colors from the docs alone will compute against the wrong palette, exactly as cycle 1 and the start of this cycle did before checking `globals.css` directly. Recommend a future small cycle just resync the docs table to match `globals.css` — pure documentation, zero deploy risk.
- **De-facto CTA blue isn't the `cra-blue` token.** Every primary CTA button site-wide (`Process.tsx`, `FAQ.tsx`, `RecentWins.tsx`, `LeadCaptureForm.tsx` submit) uses a hardcoded `#2563eb` literal — **130 occurrences across 29 files** — not the `cra-blue` design token utility class, even though `--color-cra-blue` in `globals.css` is *also* `#2563eb` (they're the same color, just one is the token and one is 130 copy-pasted literals). Functionally harmless (white-on-`#2563eb` = 5.17:1, comfortably AA-passing) but it's well past CLAUDE.md's "ad-hoc hex acceptable for one-offs only" guardrail. Flagging as a maintainability item, not touching — too broad a mechanical change for a single low-risk cycle. Separately, the two places that *do* use the literal `bg-cra-blue` token (`#3b82f6`) as a button fill with white text (`CityPageLayout.tsx:109`, `do-i-need-a-public-adjuster/page.tsx:147`) sit right at the edge — 3.68:1, which only clears AA via the large-text 3:1 allowance, and that allowance is arguable since the text is `font-semibold` (600 weight) not strictly "bold" (700). Low priority since it's borderline-passing today, but the next contrast-related cycle should double check it.
- **Minor:** `StarRating.tsx` renders 5 literal `★` glyphs inside a `<span aria-label="N stars">` without `aria-hidden` on the glyphs themselves — relies entirely on screen readers suppressing descendant content for an aria-labelled plain `<span>`, which isn't guaranteed across all screen readers. Easy fix: `aria-hidden="true"` on the glyph span. Low severity, low risk, good candidate to bundle with the `cra-dim` fix above.
- **Minor:** `LeadCaptureForm.tsx`'s phone field shows a visible error (`errors.phone`) but the `<input>` has no `aria-invalid`/`aria-describedby` pointing at it (WCAG 3.3.1/4.1.2) — a screen-reader user who fails validation isn't told why. Scoped fix, but touches the lead form's validation-adjacent markup, so flagging rather than shipping per this routine's explicit "never touch the lead form's required-field validation" guardrail — recommend the owner or a human dev review this one rather than auto-shipping it.
- Re-confirmed via lint (`npm run lint`, after `npm install` — `node_modules` wasn't present at the start of this session) that the only lint errors are the 4 pre-existing `Navbar.tsx` "component created during render" errors noted in cycle 1; unrelated to accessibility, not touched.
- Verified existing a11y coverage is solid in several areas already shipped in pre-logging commits: skip-to-content link + `<main id="main-content">` in `layout.tsx`, every `next/image` call site has a real or computed `alt`, no raw `<img>` tags except one legitimate tracking-pixel `<img alt="">` in `TrackingScripts.tsx` (Meta Pixel noscript fallback — next/image would be inappropriate here), and `LeadCaptureForm.tsx`'s labeling/honeypot/`role="radiogroup"`/`aria-label` patterns are all correct.
